# Wind Forecast — модуль 2: данные и погодные выпуски

Python 3.10+. CLI для двух ВЭУ: проверка телеметрии, почасовая агрегация,
загрузка отдельных архивных выпусков ECMWF IFS HRES, SQLite-кэш и сборка признаков.
Полные исходные файлы обеих турбин уже включены в `data/raw/`.
Модели, прогноз мощности и агентное управление относятся к следующему модулю;
этот пакет выдаёт проверяемый датасет для их реализации.

## Структура

```text
wind-forecast/
  config/config.yaml
  src/
    data/
      preprocess_telemetry.py
      fetch_weather.py
      build_features.py
    models/__init__.py
    utils/common.py
  data/
    raw/turbine_1.csv
    raw/turbine_2.csv
    processed/                 # почасовая телеметрия и отчёты качества
    cache/weather.sqlite       # создаётся при обращении к клиенту погоды
    features/                  # дневные CSV, объединённый CSV, манифест
  logs/pipeline.log
  tests/test_pipeline.py
  requirements.txt
  VERIFICATION.md
```

## Установка и запуск

Все команды запускаются из каталога `wind-forecast`, содержащего `src`.

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Установка одинаковых версий зависимостей:

```bash
python -m pip install -r requirements.txt
```

Обработать обе турбины без интернета:

```bash
python -m src.data.build_features --telemetry-only
```

Проверить полный цикл на одном дне:

```bash
python -m src.data.build_features --start 2026-01-31 --end 2026-01-31
```

Запустить диапазон из конфигурации:

```bash
python -m src.data.build_features
```

Повторить расчёт исключительно из локального кэша:

```bash
python -m src.data.build_features --start 2026-01-31 --end 2026-01-31 --offline
```

Если кэш не содержит нужного запроса, offline-режим завершится с ошибкой.
`--refresh` повторно проверяет API. Изменившиеся архивные погодные значения вызывают
ошибку: первоначальная копия остаётся для воспроизводимости. Совместное использование
`--offline` и `--refresh` запрещено.

Отдельные модули:

```bash
python -m src.data.preprocess_telemetry
python -m src.data.fetch_weather --issue-time 2026-01-31T23:00:00Z
python -m unittest discover -s tests -v
```

Для обучающей выборки с известной генерацией задайте более ранние даты:

```bash
python -m src.data.build_features --start 2025-12-01 --end 2025-12-07
```

По умолчанию метки разрешены только для интервалов, закончившихся не позднее
2026-02-01 00:00 UTC. Настройка `label_cutoff_exclusive` управляет этой границей.
Для обучения модели надо использовать строки с `label_available=True` и делить
выборку по времени, исключая пересечение целевых часов между обучением и валидацией.

## Координаты и исходное время

Координаты извлечены из перенаправлений ссылок, предоставленных в условии:

| ВЭУ | Широта | Долгота |
|---|---:|---:|
| T1 | 43.645150 | 78.535604 |
| T2 | 43.643198 | 78.538828 |

Адреса источников сохранены в YAML. Примеры координат Астаны из пользовательского
шаблона не использованы. Обе реальные серии обрабатываются независимо.
Нормализованные мощности не складываются и не переводятся в МВт без установленной
мощности каждой ВЭУ и определения нормализации.

По требованию проекта `source_timezone: UTC`. Сами CSV не содержат часового пояса:
это принятое предположение, а не установленное свойство первоисточника. Если
организаторы подтвердят локальное время, нужно задать IANA timezone в конфигурации
и повторно выполнить сборку. Вся выходная временная ось остаётся UTC.
Явные смещения во входных метках времени учитываются. Смесь меток со смещением и
без него, неоднозначное время DST и неверные даты вызывают ошибку.

По умолчанию временная метка обозначает начало интервала `[t,t+10 минут)`.
Если это конец интервала, задайте `timestamp_convention: interval_end`.
Без такого определения нельзя гарантировать правильное сопоставление часовых меток.

## Алгоритм обработки телеметрии

1. Проверяются обязательные колонки и 10-минутная сетка.
2. Полностью одинаковые дубликаты удаляются и учитываются в отчёте.
   Разные показания с одной меткой времени вызывают ошибку.
3. Числовые ошибки, бесконечности и значения за физическими границами превращаются
   в пропуски. Исходный CSV сохраняется. Целевая мощность вне `[0,1]` не обрезается.
4. Формируются все часы от первого до последнего измерения, включая полностью
   отсутствующие часы.
5. Для равных по длительности 10-минутных интервалов средняя мощность часа:

   `P_hour = (P_00 + P_10 + P_20 + P_30 + P_40 + P_50) / 6`.

   По умолчанию нужны шесть валидных значений. При пяти или меньшем количестве
   целевая мощность часа отсутствует. `coverage_power = valid_count / 6`.
   При снижении `min_valid_samples` среднее будет представлять только наблюдаемые
   интервалы; `hour_complete` всё равно обозначает исключительно полные часы.
6. Ветер и температура имеют собственные счётчики полноты. Отсутствующие измерения
   не заполняются будущими значениями; длительные простои не удаляются по статистике.

Для метки времени часа используется начало `[h,h+1h)`. В отчёте есть SHA-256
исходного файла, число пропущенных временных слотов и число пригодных целей.

## Погодный контракт и доступность в прошлом

Используется `https://single-runs-api.open-meteo.com/v1/forecast`, модель
`ecmwf_ifs`, явный параметр `run` в UTC и скорости ветра в м/с.
Запрашиваются ветер и направление на 10 и 100 м, температура 2 м, поверхностное
давление. Все запрошенные часы, единицы и физические диапазоны проверяются.
Пустые значения приводят к ошибке, а не к незаметной подмене погодой другого выпуска.

Historical Forecast API формирует сшитый ряд. Клиент намеренно разрешает только
Single Runs, потому что каждой строке нужен однозначный `run_time`.

`run_time` обозначает инициализацию модели. Она не совпадает с публикацией!
Политика по умолчанию — **явное предположение о задержке 8 часов**:

```text
run_time = floor_to_6h(issue_time - 8h)
available_at = run_time + 8h
```

Для запуска 31 января в 23:00 UTC выбирается выпуск 12:00 UTC и прогнозируются
часовые интервалы начиная с 1 февраля 00:00 UTC. При горизонте 48 часов последняя
метка — 2 февраля 23:00 UTC. Сохраняются оба горизонта:
`lead_hours = valid_time - issue_time` и
`weather_lead_hours = valid_time - run_time`.

В этих строках `availability_verified=False`, `availability_basis=assumed_delay`.
8 часов — настраиваемое консервативное допущение, не доказательство исторической
доступности. Документация поставщика также употребляет слово hindcasts для части
архива. До официальной сдачи нужно подтвердить происхождение нужных выпусков как
операционных прогнозов, доступных в соответствующие даты, и фактический лаг.
Одна только успешная загрузка архива этого не доказывает.

Для строгой проверки задайте:

```yaml
availability_policy: manifest
availability_csv: config/weather_availability.csv
require_verified_availability: true
```

CSV должен содержать колонки `model,run_time,available_at,source` с реальными
данными публикации: ISO timestamps с timezone и ссылкой/идентификатором свидетельства.
Готовый фиктивный манифест не включён. Клиент выбирает последний выпуск с
`available_at <= issue_time`. `availability_verified` здесь означает наличие
предоставленного свидетельства; его подлинность проверяет владелец данных.

## Плотность воздуха

`air_density = surface_pressure_hPa * 100 / (287.05 * (temperature_2m_C + 273.15))`

Единица — кг/м³. Это приближение для сухого воздуха у поверхности по уравнению
идеального газа, а не измеренная плотность на высоте ступицы. Влажность и градиент
температуры по высоте в этом признаке не учитываются.

## Кэш и воспроизводимость

SQLite содержит исходный JSON ответа, параметры запроса, дату загрузки и SHA-256.
Ключ включает endpoint, модель, координаты, выпуск, forecast_days, переменные и единицы.
Single Runs отклоняет start_date/end_date (проверено реальным запросом HTTP 400).
Поэтому клиент запрашивает forecast_days=7 и выбирает нужное окно локально.
Кэш одного выпуска не заменяется более новым выпуском. Координаты ячейки погоды
сохраняются отдельно от координат ВЭУ. При чтении проверяется контрольная сумма.
Транзакции защищают запись; WAL позволяет безопасно читать кэш параллельно.

Сетевые ошибки и HTTP 429/500/502/503/504 повторяются с экспоненциальной задержкой
и учётом Retry-After, максимум четыре повтора. HTTP 400 и другие постоянные ошибки
не маскируются. Повреждённый JSON и неполные данные не кэшируются.

Обновления CSV атомарны; JSON-манифест содержит конфигурацию, входные хэши,
использованные погодные ключи, версии Python/pandas/numpy и список признаков.
Дневной файл создаётся только после успешной обработки обеих турбин. При сбое
другие завершённые дни и кэш остаются доступными; повторный запуск использует кэш.

## Схема итогового датасета

Одна строка — одна турбина, один момент выпуска прогноза и один целевой час.
Первичный ключ: `turbine_id,issue_time,run_time,valid_time`.

| Группа | Поля |
|---|---|
| Время и происхождение | issue_time, run_time, valid_time, available_at, availability_basis |
| Погода | шесть запрошенных переменных, air_density |
| Горизонт | lead_hours, weather_lead_hours |
| Календарь | hour, month, dayofweek, их sin/cos |
| Направление | wind_direction_10m_sin/cos, wind_direction_100m_sin/cos |
| Цель | target_power_norm, label_available, coverage_power |
| Аудит | model, cache_key, weather_sha256, fetched_at, координаты |
| Тестовый период | in_evaluation_window |

Цель присоединяется точным совпадением турбины и начала часового интервала.
Фактический ветер и температура в этот набор признаков не включаются.
`FEATURE_COLUMNS` в коде и манифесте задаёт разрешённые входы будущей модели:
не следует передавать модели все числовые столбцы автоматически.

Циклический признак: `sin(2π*x/period)`, `cos(2π*x/period)`.
Периоды: 24 часа, 12 месяцев (с отсчётом от 0), 7 дней недели и 360°.
Погодные значения в целый час трактуются как признаки для интервала `[h,h+1h)`;
это точечный прогноз погоды, тогда как цель — средняя мощность интервала.

Конфигурация 31 января — 28 февраля включительно даёт **29 запусков**,
по 48 часов × 2 турбины = **2784 строки**. Запуск 28 февраля содержит мартовские
часы: они сохраняются с `in_evaluation_window=False`. Один час может присутствовать
в нескольких выпусках, поэтому строки разных `issue_time` не удаляются как дубликаты.
В имеющихся CSV февральских меток нет, поэтому целевая колонка тестового датасета
будет пустой. Будущие фактические значения нельзя подставлять как признаки.
